# S4.10 Run orchestrator and integrity — design (for owner approval)

**Row:** S2-M9-ENG10 · **Effort:** 1½–2 days · **Depends on:** S4.9 (`eval_score`, `eval_run`), S4.11 (reads the cell table) · **Status:** draft 2026-11-13, decisions O-a to O-j open

## 1. Scope and fixed inputs

S4.10 turns "run a variant over a corpus" into a **campaign**: a frozen schedule of every run of phase E, executed with integrity checks, exclusions, retries and resume, then bookkept into cells and the missing-data checks. Done when the full schedule dry-runs on fixtures (task breakdown). The pool stays locked until `build-freeze`, so the dry run uses fixtures and build data only.

Read-only inputs:

- `docs/tracking/s0_3_d11_corpus_run_design.md` §4 (approved D11): 8 variants × 240 cases = 1,920 confirmatory runs; 5 baselines × 240 = 1,200 baseline runs; Tier-2 variants × 240 exploratory; one registered seed per (case, variant); a **10% rerun** that measures token-sequence equality, a non-equal rerun recorded as a covariate; cells = variant × system (OB, TT) × metric, a cell enters inference only with at least 80% of its cases included.
- `helios/research/analysis_plan.py` (fingerprinted, never edited): `cell_inclusion_rule`; "MCAR test and inverse-probability weighting for exclusions" is listed under **sensitivity analyses**.
- `docs/tracking/metric_contract.md` §1 (signed, never edited): "Missing values: never imputed: a run that does not produce a metric is excluded through the integrity gate, with an exclusion-ledger entry and its covariates."
- `helios/research/seeds.py`: `run_seed(case, system, case_order)`, slots for all 15 variants and 5 baselines; `opaque_id_seed`. Any new seed block needs a deviation entry.
- S3 plan and `s3_3_reward_design.md` W-b: the E-H5 replay runs after confirmatory scoring on a "seeded 25% of each pool corpus"; its selection rule is fixed before `build-freeze`.
- S4 plan notes on S4.10 and `s4_d11_compute_recheck.md` §5: a fixed first variant per case fills the response cache and sets the wall times later variants replay; the run order is recorded; the determinism rerun bypasses the cache; exploratory variants whose flag has no consumer are refused.

## 3. Decisions (for approval)

### O-a. The schedule: one frozen, pure list of runs

- A `RunSpec` is (phase, corpus, case, system, registered seed, position, cache mode). The schedule is generated by a pure function of the sealed corpus manifests (`case_order`), the variant catalogue and the baseline list. The same inputs give byte-identical `schedule.json`; its SHA-256 is recorded in every run row and in the campaign's reconciliation entries.
- **Phases**, in execution order:
  1. **P1 confirmatory:** 8 variants × 240 = 1,920.
  2. **P2 baselines:** 5 × 240 = 1,200 (stub executor until S4.8).
  3. **P3 exploratory variants:** each Tier-2 variant that has a flag consumer (O-h) × 240.
  4. **P4 scoring and the score-time gate** (O-c), then cells (O-e).
  5. **P5 determinism rerun** (O-g).
  6. **P6 E-H5 delayed-label replay** on the subset (O-g), after P4.
  7. **P7 OTel v4 report** (exploratory, not pool), only if that corpus exists by then.
- `run_id` becomes deterministic: SHA-256 of (schedule digest, phase, case, system, attempt), shortened. A random UUID makes two executions of the same schedule incomparable row by row.
- The registered `run_seed` is recorded in every run row (D11 requires one per case and variant). HELIOS uses greedy decoding, so it changes no output today; the baselines read it.

### O-b. Order inside phase 1: case-major, HELIOS-noRouter first

- **Recommended:** case by case. Within a case, **HELIOS-noRouter first**, then the other seven in Ch3 Table 17 order. noRouter calls every L-pipe worker on every case, so its calls fill the cache, and every later variant of that case replays the same worker wall times. If the fixed first variant were one that sometimes skips the L-pipe, the first L-pipe caller (and so the replayed wall time) would differ from case to case.
- Case-major also means an interruption leaves whole cases, never a variant that has run on more cases than its partner.
- (b) Variant-major (today's pattern: one variant over the corpus, then the next). It is simpler, but the cache-filling run then depends on the variant order, and an interruption leaves unequal cells.
- The executed order (position, start and end time) is recorded per run in the campaign table.

### O-c. Run outcomes: passed, excluded, retried, or campaign stop

| Outcome | When | Recorded |
|---|---|---|
| **passed** | Integrity checks pass | Result rows, CoE entry, reconciliation `passed` |
| **excluded** | Capture hash or seal invalid; gate failure (fields, config hash, snapshot consistency); a run error that is not infrastructure; retries exhausted; at score time, a registered metric missing for the run | **Exclusion-ledger entry with covariates** (O-d) and reconciliation `excluded`. Today hash and seal failures write only `skipped`; under the contract they are exclusions |
| **retried** | Infrastructure errors only: the model server unreachable or timed out, out of memory, the process killed. Up to **2 retries**, same inputs, cache as the schedule says | Reconciliation `retry` with the attempt number. Retry is decided by the exception class, never by the result, so it cannot select outcomes |
| **campaign stop** | Configuration refusals: provisional parameters, missing signing key, router/price-book mismatch, external trigger in confirmatory, pool locked, model digest mismatch | The campaign stops before writing anything for that run. These are setup faults, not run outcomes; excluding them would turn a setup fault into missing data |

- A run error that is not infrastructure is excluded, with the exception class and a digest of the traceback in the ledger, and the campaign continues. Today it aborts the corpus.
- `llm_unavailable` runs (S3.5 fallback) stay **passed**, with the covariate, as now.
- **Score-time gate:** after P4 scoring, every run is checked for each registered metric of its cell set (HR@1/3/10, Avg@5, CpR, TTCD, TTT; H_fact only when labels are due). A missing metric excludes that **run for that metric only**, since cells are per metric. A censored TTCD is a value, not missing. HR@k of an empty list is 0, not missing.
- One transaction per run for the store writes, so a crash never leaves half a run. On resume (O-i), a run without a final reconciliation record is re-run from scratch.

### O-d. Exclusion entries: covariates, and one ledger per campaign

- The 7 required fields stay. Added, signed fields: `phase`, `corpus`, `system`, `variant`, `metric` (or `all`), `attempt`, `schedule_digest` and `covariates` (canonical JSON).
- **Covariates written at run time are label-free only:** window bytes, number of observed services, modalities present, signal type, trigger source, escalated, `llm_unavailable`, wall time. Ground-truth covariates (fault type, root-cause service, group) are **never** written by the run path; the analysis joins them from the signed ground truth under the pool lock.
- **Ledger location:** the root `exclusion_ledger.jsonl` (empty, anchored) is reserved for the confirmatory pool campaign. Every build, fixture or dry-run campaign writes its own anchored ledger inside its campaign directory. Otherwise a dry run would put entries into the ledger the OSF deposit cites. `bin/verify_ledgers.py` gains a `--campaign <dir>` option.
- `bin/log_exclusion.py` loses the "Stage 1+ stub" wording and accepts the new fields for manual entries.

### O-e. Cells and how a failing cell enters the tests

- A cell is (system, variant or baseline, metric). Its share is included runs ÷ scheduled cases of that system. The table goes to `cells.json` in the campaign directory, with counts per exclusion reason.
- **Recommended (a):** a cell below 80% leaves inference. A hypothesis is tested on the cases of the systems where **both** of its compared cells pass, paired by case as before. If no system passes for both, the hypothesis is untestable (counted, never dropped, as S4.11 does now). The report states which systems each hypothesis was tested on.
- (b) Strict: any failing cell of a hypothesis makes the whole hypothesis untestable.
- (c) Today's interim S4.11 rule: one 80% threshold on the hypothesis's paired cases, ignoring systems.
- Under (a), S4.11 reads `cells.json` and the interim `CELL_INCLUSION` rule is retired. Strata (A-H4, A-H6) do not define cells; they are subsets of the cases a passing cell already admits.

### O-f. MCAR test and IPW (sensitivity, as the plan lists them)

The plan lists both as sensitivity analyses, so neither can change a binding result. With the expected exclusion counts (probably a handful), a large-sample test would be meaningless; the design follows the count.

- **Unit:** the case-pair of a hypothesis. A pair is missing when either run is excluded, or its cell fails, for that metric.
- **MCAR test (recommended):** per hypothesis, a logistic regression of "pair missing" on system, fault type, window bytes and observed services; a likelihood-ratio test against the intercept-only model. It is run only when there are **at least 10 missing pairs** (the usual events-per-variable floor for this many covariates). Below that, the report lists exact per-covariate comparisons (Fisher's exact test for system and fault type; exact rank-sum for the continuous ones) as descriptive, with the count. With no missing pair, the report says "complete; MCAR not applicable".
- **IPW:** when a hypothesis has any missing pair, fit the same logistic model for "pair complete". Use stabilised weights (marginal completion share ÷ fitted probability), truncated at the 1st and 99th percentiles. Report the weighted mean paired difference with a weighted BCa interval, seed `bca_seed` of that hypothesis, beside the binding test, and say whether the sign agrees. A weighted Wilcoxon has no standard exact form, so no weighted p-value is reported.
- (b) Little's MCAR test: rejected. It assumes multivariate normal outcomes, and the outcomes here are 0/1 and heavily tied.
- The code lives in `helios/analysis/missing.py` and is called by `bin/analyse.py`, so the analysis stays one command.

### O-g. Determinism rerun and E-H5 subset: selection without a new seed block

Both subsets need a reproducible random selection. The case order is already random: it is the sorted list of opaque IDs, which are drawn from the register (`opaque_id_seed`). So a fixed stride in that order is a seeded random sample without a new seed block, and needs no new deviation for seeds.

- **Determinism rerun (recommended):** every 10th case of each system's `case_order` (positions 9, 19, …; about 24 cases of 240). All HELIOS variants that call the model are re-run on those cases with the cache **bypassed**, into a separate rerun store, so S4.11 never sees duplicate runs. Compared per run: worker output text, narrative text and the fused list. A non-equal run gets `nondeterministic = true`, a covariate joined into `eval_run`. Run ranges per variant, not per call, keep the cost as in the compute recheck.
- **E-H5 subset (recommended):** every 4th case of each pool system's `case_order` (positions 3, 7, …), so 25% per system as S3.3 requires. This rule goes into the addendum before `build-freeze`, as W-b requires.
- (b) A new seed block in the reserved range, with a seeded shuffle. It is more conventional, but it needs a register change and its own entry.

### O-h. Refusing exploratory variants that equal Full

- **Recommended:** an AST scan of `helios/` and `bin/` (excluding `helios/vcl/` and tests) for reads of each boolean flag (`manifest.<flag>`, `VCLFlag.<FLAG>`, `@gated_by(VCLFlag.<FLAG>)`). A variant whose OFF flag has no reader is refused from the schedule, with the reason in `schedule.json`. Today that refuses noCogni, HIS3, noFGSV and noIOL; noFGSV and noIOL return once S4.6 and S4.7 add readers.
- The scan is the same one the S5.2 disjointness certification needs, so it is built once in `helios/vcl/catalog.py` (helpers go there, never in `variants.py`).
- A confirmatory variant is never refused: all 8 have readers today, and a missing one stops the campaign.

### O-i. Campaign directory, resume and the CLI

- `bin/helios_campaign.py plan | run | resume | status | cells` over one campaign directory. The directory holds `schedule.json`, the result store, the reconciliation and exclusion ledgers, the CoE files, `cells.json` and the run-order table.
- `run` refuses a directory whose schedule digest differs from the regenerated one. `resume` skips specs with a final `passed` or `excluded` record and re-runs the rest from scratch (O-c transaction).
- A pool campaign is refused before `build-freeze` (`pool_lock.require_unlocked`), the same as the adapter.
- The runner change is small: a public `run_incident(incident_id, run_id, seed)` that returns the outcome instead of looping a corpus, plus the error classes of O-c. `RunOrchestrator.run()` stays for the existing scripts. One orchestrator per variant is built once per campaign (one manifest each), and the `ContextVar` manifest is set before every run.

### O-j. What "dry run of the full schedule" means

1. **Full-size schedule, stub executor:** a fixture pool manifest (240 opaque cases, 2 systems, 78 groups, no real data). The plan and checks: counts per phase (1,920, 1,200, exploratory, rerun and E-H5 subsets of about 24 and 60 cases), every seed unique and inside the run block, noRouter first in every case, the refused variants listed, and a byte-identical digest on regeneration. Execution through the stub, with injected faults: a seal failure, an infrastructure error that recovers on retry, one that exhausts its retries, a non-infrastructure error, a missing metric at score time, and a kill-and-resume. Then cells, the cell rule, MCAR (both branches) and IPW on the result.
2. **Real execution on build data:** OTel build v3, 8 confirmatory variants, cache-only client, through the campaign runner. It must reproduce the S4.11 build run's scores exactly (same `eval_score` rows apart from `run_id`). This shows the campaign changes no result.

## 4. Deviation entry

The rules in O-a to O-g decide which runs count and how missing data is reported, so they are recorded before any confirmatory data exists. As with entries 84 and 86, there is one entry after approval, and the rules go into the OSF addendum draft (S2-BL-05). The entry covers:

- the outcome classes and retry rule (O-c);
- the score-time exclusion per metric (O-c);
- the ledger covariates and per-campaign ledgers (O-d);
- the cell rule's application (O-e), which replaces the S4.11 interim rule of entry 86 item 9;
- the MCAR and IPW methods (O-f);
- the stride selections for the rerun and E-H5 (O-g).

The hypotheses, metrics, analysis plan, metric contract and variant hashes are unchanged.
